# 本番反映前の再確認

確認日：2026-09-09。対象は、役割別DM・予約メッセージ画面・本文検索・共通ブロック・取消/返金・ローカル模擬決済を含む今回の変更全体。前回の[影響確認](本番反映前の影響確認_2026-09-09.md)後の追加実装も含めて確認した。

## 結論

**確認した範囲で、変更前に比べて新たな既存テストの失敗はない。ただし、全体テストは既存の問題により完全成功ではなく、本番公開の判断には開発環境での外部連携確認が残る。**

今回は決済確認の競合と配信ファイルの扱いを修正した。本番・stagingへのデプロイやマージは行っていない。既存のローカルDBも変更せず、MySQLの検証には専用の一時サーバーと架空データを使用し、終了後に試験DBを削除して専用サーバーを停止した。

比較基準は最新のリモート参照を取得して確認したstaging `d4ff9e20d5d822796fca784e54dd0f81c3992ea9`、main `8756520b182a8d9c6019bdf58945a63766eafaca`。改修前の比較はstagingのソース・テストを隔離し、同じ依存ライブラリで実行した。

## 見つけて修正した問題

### 決済確認の遅延応答が新しい状態を上書きする

Stripeへの確認を待つ間に決済をやり直したりキャンセルが成立した場合、古い決済の応答を現在の決済に適用できていた。新しい決済を誤って認証済みにしたり、取消済みの状態を戻したりする余地があった。

ネットワーク応答後にロックを取得し、予約状態・決済レコード・決済状態・最後に処理したWebhookが問い合わせ前の状態と一致する場合だけ反映するよう変更した。予約の応答は最新状態を再取得する。決済の差し替えとキャンセルの2つの再現テストは修正前に失敗し、修正後に成功。通常の認証完了も申込済みへ遷移し、再確認で状態変更を二重記録しないことを確認した。

### 配信時にローカルDBや設定が混ざる／開発環境を消す余地がある

既存の配信スクリプトはGitの追跡状態と関係なくファイルを同期するため、今回の確認用SQLite DBやローカルの設定・ルートキャッシュが成果物に混ざる状態だった。また、本番の公開フォルダ内にある開発環境と証明書確認用フォルダが削除同期の保護対象になっていなかった。

- SQLiteファイルと補助ファイルを成果物作成・アプリ同期の両方から除外。
- ローカルのPHPキャッシュを成果物作成時に除外。Composerが依存関係に合わせて生成する情報は配信し、古いサーバー側の設定・ルートキャッシュは通常の同期で削除する。
- 公開資産の同期で `dev.sugutachi.com/` と `.well-known/` を保護。
- 実際のスクリプトから同期条件を読み、一時フォルダ間でrsyncを実行するテストを追加。ローカルデータの非混入、既存の環境ファイル・アップロードの保持、新しいコードの反映、古い資産の削除、開発環境と証明書用ファイルの保持を確認した。SSHや実際の配信処理は実行していない。

## 既存の仕組みとの接続確認

| 領域 | 確認内容 |

| 役割とプライバシー | 逆役割のDMを別会話として扱い、第三者・違う役割からの本文/画像取得を拒否。本文検索も閲覧可能な範囲だけを対象とする |
| 既存予約メッセージ | 送受信、既読、画像、クローズ、履歴の閲覧制限を既存テストで確認。DMへの統合や既存データの移し替えなし |
| 予約から売上まで | 申込・承諾・開始・完了、決済認証/売上確定、取消・返金、定期処理の既存テストを実行。外部決済は模擬 |
| ブロックと精算 | 開始前予約の取消、開始後の運営確認、返金再試行、二重精算の抑止、旧ブロックとの互換性を確認 |
| MySQLの同時操作 | 同じ初回送信を2プロセスで実行して会話・本文が1件だけ作られる。ブロックがロックを保持している間は送信が待ち、ブロック完了後に409で拒否される。対象予約は取消済みで追加本文は保存されず、逆役割のDMは送信できる |
| データ移行 | MySQLでもmigration往復を実行し、旧予約の本文レコード・クローズ状態・旧ブロックの保持を確認 |
| 通知・管理・保存 | 通知の役割分離/抑止、証拠閲覧権限、保存期限、削除履歴の復元、精算保留の管理をテスト |
| 模擬決済の隔離 | local・専用SQLite・ループバックURL・明示設定・Stripeキー未設定の条件を確認。production/staging/MySQLでは有効にならない |
| 画面 | 今回も型チェック・ビルド成功。直前の画面検証では両役割、PC/幅320px、予約詳細への遷移、情報メニューの開閉、クローズ確認の取消を確認済み。今回の再確認によるUI変更なし |

同時操作は一時MySQL上の実サービス処理を別プロセスから呼んだ検証であり、共有サーバー上の高負荷試験やStripeを含む全競合パターンの保証ではない。

## 変更前から残る失敗

- SQLiteの4件：送金可能判定、キャストプロフィールの復旧理由、規約草案の期待値、空き枠見積額。詳細は前回レポート参照。
- MySQLの10エラー：空き枠8件、キャスト検索1件、料金ルール1件で、テスト用アカウントの公開IDがカラムの最大長を超えている。対象の検証処理に到達する前に失敗する。
- MySQLの6失敗：送金可能判定、プロフィール復旧理由、規約草案、およびサポートの段階配信3件で対象件数が期待と合わない。

いずれも変更前stagingで再現する。ただし「既存の問題だからサービス運用に問題がない」とは判断していない。送金・見積・段階配信は業務上の影響と正しい期待値の整理が必要。MySQLのテスト用データの修正も別途必要となる。

## 公開前の残りの条件

1. stagingへ反映し、Stripeテスト実接続でカード認証・3Dセキュア・認証取消・部分返金後の残額返金・接続先送金の巻き戻し・遅延/重複Webhookを確認する。ローカル模擬決済とHTTP応答の置き換えだけでは代替できない。
2. 実際の開発環境で、毎分の定期処理、共有ロック、試験用メール・プッシュ配送、運営の精算確認、バックアップ/復元と世代保持を確認する。
3. 検索履歴の多い複数アカウントで同時検索の負荷を測定する。暗号化本文の検索は履歴量に比例し、これまでのローカル計測は本番性能の保証ではない。
4. 上記の既存失敗の業務影響を整理したうえで公開を判断する。
5. リリース時はDB・非公開ファイル・鍵をバックアップし、メンテナンスとワーカー/定期実行の停止を行ってからコードとmigrationを反映する。DMフラグOFFだけでは新テーブルへのアクセスを全経路で回避できない。配信スクリプトは自動でメンテナンスに入らず、migrationには `--migrate` が必要。移行・設定・既存予約データの照合後に処理と公開を再開する。

## 再実行の入口

- PHP全体：`APP_NAME=すぐタチ APP_URL=http://localhost vendor/bin/phpunit`（試験用DBを使用）。
- 配信条件：`python3 tests/deployment/test_artifact_filters.py -v`。一時フォルダだけを使用する。
- フロント：`npm run typecheck`、`npm run build`。
- MySQLで再実行する際は、必ず専用の破棄可能なDBを用意する。LaravelのテストはmigrationによるDB初期化を行うため、既存の開発DB・本番DBを指定しない。
