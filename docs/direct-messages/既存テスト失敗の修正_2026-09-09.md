# 既存テスト失敗の修正

2026-09-09。本番反映前の[再確認](本番反映前の再確認_2026-09-09.md)で残っていた失敗を、ユーザーの依頼に基づき原因別に修正した。

## 原因と対応

| 対象 | 原因 | 修正・確認 |
| --- | --- | --- |
| サポートの段階配信 | MySQLのTIME型に対し、バインド値を使うIN検索では設定時刻に一致するシナリオが取得できなかった。単独実行でも既存3テストが失敗 | 時刻の等価比較を括弧内のOR条件に変更。SQLiteの「時:分」形式にも対応し、有効シナリオだけを処理する。修正後はMySQLでも既存3件が成功 |
| Stripeの送金可能判定 | 手動振込方式追加後も、テストが送金方式を指定せずにモデルを生成していた | Stripe Connectを明示した試験データに修正。手動振込・方式未指定ではStripe送金不可の検証も追加。サービスの送金判定は変更しない |
| キャストプロフィール復旧 | 公開条件の自動判定導入（`a20a96b`）以降は、復旧時の現在の却下理由を解除するが、テストは古い理由の保持を期待していた | 現在の理由はnull、過去の停止理由は管理監査ログの変更前情報に残ることを検証。公開・復旧処理は変更しない |
| 規約の草案同期 | テストのバージョン・タイトルが旧MVP草案のままだった | 現在の設定（2026-04-28・利用規約）に更新。公開済み本文を上書きせず、草案だけを更新し、重複作成しないことも確認。規約本文・公開状態は変更しない |
| 空き枠の見積額 | 固定の距離/深夜加算廃止（`e43f6cc`）以前の期待値だった | 料金ルールなしでは基本12,000円＋手数料300円。距離条件に1,000円加算するルールを明示すると範囲が12,300〜13,300円になることまで検証。サービスの料金計算は変更しない |
| MySQLのデータ長エラー | 空き枠・キャスト検索・料金ルールの試験データに、36文字を超えるアカウント公開IDがあった | 該当箇所を既存のFactoryによる正規のID生成に変更。DBカラム長や入力検証を緩めず、止まっていたテスト本体まで実行 |

この修正で本体の動作が変わるのはサポート段階配信の時刻検索。その他は、実装・変更履歴を確認したうえで試験データと期待値を現行仕様に合わせ、検証を追加した。

## 追加した回帰確認

- 段階配信：00:00、09:05、20:00、23:59、秒あり/なし形式。予定時刻前には送らず、その分内の処理で1回送信する。再実行で二重送信せず、次の分には対象外。草案シナリオも配信されない。
- Stripe：正規ID・Connect方式・課金有効の組合せ、課金無効、プレビューID、手動振込方式、方式未指定。
- 復旧：現在の停止理由解除と、変更前の理由が監査履歴に残ること。
- 草案同期：公開済みレコードの保持、未公開草案の更新、繰り返し同期で件数不変。
- 見積：明示的な距離料金ルールの有無で金額範囲が変わること。

## 最終検証

| 環境 | 結果 |
| --- | --- |
| SQLiteメモリDB | 377件すべて成功、3,267 assertions |
| 隔離MySQL 8.4.9 | 377件すべて成功、3,267 assertions |
| 変更したPHPの書式・差分整合性 | 成功 |

全体テストには既存の予約、決済、返金、DM、ブロック、管理、通知、migrationの検証を含む。前回のSQLiteの4失敗、MySQLの10エラー・6失敗は解消した。新規6ケースも両DBで成功。専用MySQLの試験DBは実行後に削除し、専用サーバーも停止した。

画面・依存ライブラリ・DBスキーマの変更はないため、フロントのビルドは前回の成功結果を継続利用する。

## リリース上の注意

本番・stagingへの反映、実際のメール/プッシュ送信、既存DBの更新は行っていない。検証は架空データ・外部送信の模擬を使用した。

段階配信の修正を反映すると、これまで時刻検索に一致せず処理されなかった有効シナリオが予定時刻に動作する可能性がある。既存の配信済み判定・同名チケット除外・1日上限は維持しているが、**反映前に管理画面のプレビューで各有効シナリオの対象件数を確認し、開発環境の試験送信先で動作確認すること。**

全体テストの成功はStripe実接続や共有サーバーの実通知確認を代替しない。本番公開前には、再確認レポートの外部決済・定期処理・通知・バックアップ/復元・負荷の確認を継続する。
