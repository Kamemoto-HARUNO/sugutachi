**2. キャストのブロックと予約取消：推奨案**

施術開始前なら「連絡できない予約を残す」より、キャスト都合の取消と利用者負担ゼロを同時に処理する方が分かりやすい。既存BookingCancellationPolicyもキャスト都合をキャンセル料0円としており、この考え方に合わせられる。ただしサービス提供済みの代金までブロックで無条件に取り消さないよう、開始前と開始後を区分する。

対象は、ブロックしたキャストが受ける、同じ利用者からの予約すべて。同じ向きで今後3件の予約があれば3件とも対象にする。DMからの予約か直接予約かでは分けず、逆役割の予約は含めない。

| ブロック時の状態 | 予約処理 | お金の処理 |
|---|---|---|
| 予約なし | 新規DM・予約を拒否 | なし |
| 決済認証中・依頼中（payment_authorizing / requested） | 未承諾の依頼を終了。決済中止／見送りという既存状態の意味に沿って処理 | 未請求は請求しない。確保済み枠は解除。例外的に請求済みなら未返金残額を全額返金 |
| 承諾済み・移動中・到着済み（accepted / moving / arrived） | キャスト都合で全対象をキャンセル | 利用者負担0円。確保した利用枠の解除、または請求済み未返金残額の全額返金 |
| 施術中・キャスト完了報告後（in_progress / therapist_completed） | 接触を即停止し運営確認。単純なキャンセルへ自動変更しない | 提供状況を確認して精算・返金判断。必要な個別保留を行うが、無関係な売上は止めない |
| 未着申告等の係争確認中・中断案件 | 接触を停止し、既存の案件を運営対応へ接続 | 争点を確認して判断。通常の開始前取消で係争手続きを上書きしない |
| 完了・取消・見送り・失効等の終了済み | 過去予約を変更しない | ブロックだけでは新たな返金をしない。既存の未完了返金処理は継続 |

ブロックする側が利用者の場合は、DM・予約チャットの接触は停止するが自動的な無料キャンセルはしない。利用者からの取消は既存の取消条件へ案内する。運営への問い合わせは常に残す。

**キャスト向けの操作**

同じ向きの有効予約がある場合、確認画面に対象予約、件数、利用者負担0円となる金額、運営確認に回る案件を明示する。送信停止だけの操作に見せず、開始前予約がある場合の主ボタンを「ブロックして予約をキャンセルする」とする。確認して確定した後、予約ごとに再び取消操作を求めない。開始後のみなら「ブロックして運営に相談する」とする。

確認画面を開いてから状態が変わった場合は、サーバーで再確認する。接触停止は確実に保存し、開始済みになった案件を開始前として返金しない。変更後の処理結果を示す。複数予約の処理状態は個別に管理し、一部の精算が未完了でもブロックを解除しない。

利用者へは「キャスト都合で予約がキャンセルされました」「返金手続き中」等の業務通知を届け、別役割やブロック設定元の情報は出さない。ブロック解除後も予約は復活させない。希望する場合は新しい予約として作り直す。

**既存実装から必要になる変更**

- 既存のキャスト取消APIはaccepted / moving / arrivedを許可し、未着申告の確認待ちを拒否する。承諾前の処理は見送り・認証解除へ分岐する必要がある。
- キャスト取消のpolicyは0円を返すが、精算のpayment_actionはvoid_authorizationである。既存の認証解除サービスはsucceededを何もせず返す。このため、請求済みの場合まで既存呼出しだけで「返金完了」としてはいけない。
- 全額返金とは、当該予約で実際に請求した額から返金済み額を引いた残額。利用者へマッチング料・キャンセル料・決済処理費用を差し引かない。無料予約や未請求予約へ返金を作らない。
- Stripeでは未確定の請求はキャンセル、確定した支払いは返金という別の処理で、返金が保留・失敗になる場合もある。予約取消と返金状態を分け、完了前は処理中と示す。[Stripe公式：支払いの返金とキャンセル](https://docs.stripe.com/refunds?locale=ja-JP)
- ブロック・対象予約の取消状態・決済対応ジョブを同じ保存単位で記録する。外部決済の応答不明時は状態を照合し、安定した冪等キーと予約ごとの精算記録を使って二重返金を防ぐ。Webhook重複・再試行も同様。
- 売上・返金台帳、キャンペーンの復元、キャスト都合キャンセル件数、通知を整合させる。既存の取消回数から自動除外しない。安全上の事情による個別配慮は運営が監査付きで判断する。

**3. 画像送信の具体仕様**

既存BookingMessageController.storeの条件を基準に、1送信で画像1枚、10,240KiB（10MiB）以下、JPEG・PNG・WebPを許可する。本文と画像を同時に送る形ではなく、文章メッセージと画像メッセージを別々に送る。送信前プレビュー、削除済み表示を用意し、画像も未読・通知・送信上限・人の返信の対象にする。返信前3件の上限は画像を含めて数える。この上限自体は初期提案値。

既存と同じ操作感にしつつ、DM画像の取得はログインと固定参加役割で認可する。画像は非公開領域に置き、プロフィール画像や予約添付へ流用しない。位置情報などのEXIF、元ファイル名、所有アカウントIDを相手へ渡さない。旧機能の署名リンクだけの認可をそのままコピーしない。

送信者はブロック後でも自分の画像を削除できる。双方に削除表示を残し、旧リンク・サムネイルは即取得不可にする。端末へすでに保存された画像を遠隔で消せるとは案内しない。通報保全の必要があれば運営専用に分け、相手向け画像を再公開しない。画像内の連絡先を既存のテキスト検知で検出済みとは扱わない。

**4. 保存期間・削除の推奨案**

DMは事前相談が主目的で、予約成立後の正式な連絡は別チャットに残る。長期間の一律保管を避けつつ、相談の再開や問い合わせに対応できる初期案として、以下を提案する。いずれも現行稼働仕様・法定年数ではない。

| 対象・操作 | 推奨期間・扱い | 意図 |
|---|---|---|
| 通常のDM本文・画像 | 各メッセージの送信から1年で削除 | 同じ期限で分かりやすく管理し、不要な長期蓄積を避ける |
| 新着・既読・アーカイブ・ブロック | 過去メッセージの期限は延長しない | 少しの再開で何年分もの内容が残り続けないようにする |
| 送信者による画像削除 | 即時に取得停止、通常保存先・派生画像から24時間以内に削除 | 個別画像を早く取り下げられるようにする |
| 退会時のプロフィール | 即座に退会表示へ変更し、名前・写真・リンクを非表示 | 退会後の相手向け表示を最小化する |
| 退会者が送ったDM | 通常の1年期限と退会90日後の早い方で削除。添付画像は退会時に取得停止 | 問い合わせ・通報を受ける期間を限定して確保する |
| 退会者とのDMで、相手自身が送った内容 | 通常の1年期限。退会者の情報を新たに補完しない | 相手の送信履歴を退会だけで一括削除しない |
| 通報・返金等で保全が必要な原文 | 対応中は必要部分を運営限定で保持。90日ごとに必要性を見直し、解決後原則1年で削除 | 一般のDM保存と証拠保全を分ける |
| 特別な継続保全 | 理由・責任者・期限／次回見直し日を登録して必要な部分だけ延長 | 「通報あり」を理由に無期限放置しない |
| バックアップ | 通常保存先から削除後、最大35日で世代から消える構成を目標 | 削除済みデータが復元で復活しない運用にする |

期限到来後は利用者だけでなく通常の管理画面・検索・キャッシュからも対象を除去し、本文や画像を含まない最小限の削除記録を残す。空になったDMは固定された役割の関係とブロック判定だけを維持できるが、原文や相手の過去プロフィールは復元しない。保全が不要になれば内部記録も見直す。

削除は日次処理とし、期限を過ぎた内容は取得APIで直ちに非表示、通常保存先から24時間以内に消す。送信時刻を期限の基準とし、画面の案内は「DMのメッセージと画像は送信から1年間保存されます」とする。退会時には90日以内の削除と保全例外を案内する。一般ユーザーの全文削除機能を新たに必須とせず、本文の削除・利用停止依頼は運営窓口で扱う。保存期間内だからという理由だけで依頼を一律拒否しない。

バックアップの削除方式・35日の上限は現在の構成を未確認。実装前に実現方法を確認する。削除履歴を通常DBと同じ古い状態へ戻さず、復元環境を公開する前に最新の削除履歴・退会・ブロック・保全状況を適用する。

既存AccountWithdrawalServiceは退会状態の更新・認証解除等を行うが、DM原文の期限削除をすでに実施しているわけではない。またローカルの法務文書テンプレートは保存期間管理という方針を記載しているものの、DMの具体的な年数は定めていない。公開中の文書本文・予約記録の保存期間は別途照合する。予約・決済・返金記録へこの1年ルールを一括適用しない。

個人情報保護委員会の説明では、個人情報保護法は一律の保存期間を定めず、利用する必要がなくなった個人データは遅滞なく消去するよう努めるとしている。このため上記の1年・90日等は、相談対応・プライバシー・紛争対応の用途を踏まえたサービス運用の推奨値であり、法律が要求する年数ではない。[個人情報保護委員会：取得した個人情報の廃棄時期](https://www.ppc.go.jp/all_faq_index/faq1-q5-2/)
