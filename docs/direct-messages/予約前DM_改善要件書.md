**1. 今回の確定方針**

1アカウントが持つ「利用者としてのプロフィール」と「タチキャストとしてのプロフィール」は別の対外的な身元として扱う。利用者として相談・予約した行動が、本人のキャスト活動とシステム上で結び付いて相手に見えないようにする。

予約に依存しない事前DMを新設する。DMは利用者側とキャスト側の役割を固定して管理する。予約が作成されたら、その予約については既存の予約ID別チャットを使う。DMと予約チャットは、本文・履歴・既読・通知・終了状態を独立させる。キャストによるブロックは、その対象からのDMと予約受付の両方へ適用する。

| 会話 | 参加者 | 管理単位 | 他の会話との関係 |
|---|---|---|---|
| 事前DM① | Aの利用者プロフィール ↔ Bのキャストプロフィール | この役割付き組み合わせで1件 | 事前DM②と完全に別 |
| 事前DM② | Bの利用者プロフィール ↔ Aのキャストプロフィール | この役割付き組み合わせで1件 | 事前DM①の存在・履歴を知らせない |
| 予約チャット① | 予約R1の利用者 ↔ 予約R1のキャスト | 予約R1 | DM①から本文を移さない |
| 予約チャット② | 予約R2の利用者 ↔ 予約R2のキャスト | 予約R2 | 同じ相手でもR1と分ける |

利用の流れは「キャストのプロフィール → 利用者としてDMで相談 → 必要なら既存の予約画面 → 見積もり・本人確認・予約手続き → その予約のチャットで連絡」。直接予約も継続できる。予約後もDMは残るが、予約の履歴には変換しない。

**2. 役割とプライバシー（DM-01〜03）**

**DM-01：役割固定の会話。** DMの一意性は「利用者プロフィールID × キャストプロフィールID」で判定する。内部の所有アカウントIDは認証・不正防止・ブロックのために持てるが、2つのアカウントIDを並べ替えて会話を統合しない。役割を反転した組み合わせは別の会話ID、別の未読、別の設定を持つ。会話作成後に参加者や役割を入れ替えない。

**DM-02：相手へ見せる情報を役割別に限定する。**

| 項目 | 利用者として参加 | キャストとして参加 |
|---|---|---|
| 名前 | 利用者側で設定した表示名 | キャストの公開名 |
| アイコン | 利用者用に設定した写真、未設定なら汎用アイコン | 公開可能なキャスト写真、未設定なら汎用アイコン |
| プロフィールリンク | 必要最小限の利用者向け表示のみ | 当該キャストの公開プロフィール |
| 相手に渡す識別子 | 利用者専用の公開ID、またはこの役割の参加者ID | キャストプロフィール公開ID、またはこの役割の参加者ID |
| 渡さない情報 | キャスト兼任の有無、キャスト名・写真・URL・実績 | 利用者側の表示名・写真・利用履歴 |

キャスト名未設定時に共通アカウント名を出す、利用者アイコン未設定時にキャスト写真を使う、といった代替表示を禁止する。アカウント共通ID、全保有ロール、last_active_role、メール、電話番号、同一人物の別プロフィール対応表を相手向けAPIに含めない。会話本文だけでなく一覧、通知、検索候補、画像URL、ブロック一覧、通報後の表示、予約チャットの送信者表示にも適用する。

DMでは利用者プロフィール全体を自動共有しない。健康情報、詳細な希望、住所などを既存の自分用プロフィールAPIから流用しない。本人が自ら同じ名前・写真を使うことや本文で自己紹介することによる推測まで防ぐものではないが、システムは別役割を開示・紐付けしない。

**DM-03：現在の操作役割を明示する。** 利用者用画面には利用者としてのDM、キャスト用画面にはキャストとして受けたDMのみを表示する。宛先選択・送信欄には「利用者として送信」「キャストとして返信」が分かる表示を置く。URLの役割と参加役割が一致しない場合は本人に役割切替を案内し、勝手に切り替えて送信しない。

認可はログイン中のアカウントがその役割のプロフィールを所有することを毎回サーバーで確認する。別タブのロール切替で既存画面の送信人格を変更しない。下書き、キャッシュ、入力中、通知リンクをDM IDと操作役割で分離する。共通のlast_active_roleだけで送信者の役割を決めない。

**3. 開始・一覧・送受信（DM-04〜06）**

**DM-04：利用者から開始する。** 有効なアカウントでログインし、利用者ロールを持つ人が、公開条件を満たしDM受付ONのキャストへ最初の文章を送れる。本人確認・決済・予約作成は事前DMの必須条件にしない。オフラインや予約枠なしでもDM受付ONなら相談可能。自分が所有するキャストプロフィールへの送信は禁止する。

利用者プロフィールの行・公開IDが未作成なら、初回送信時に本人の利用者用情報として最小限の行を作る。キャスト名・キャスト写真を流用せず、必要な利用者表示名がなければ利用者用の名前入力へ案内する。プロフィール完成・本人確認を勝手に完了扱いしない。

最初の文章の保存と会話作成を一体で行う。画面表示や入力だけではDMを作らず、通知もしない。同じ役割付き組み合わせへの連打・同時送信でも会話は1件にする。未ログインなら対象と利用者役割を保持してログインへ戻し、復帰時に自動送信しない。

**DM-05：DMと予約連絡を区分する。** 各役割のメッセージ画面に「DM」「予約の連絡」を分けて用意する。DMタブは役割付きの相手単位、予約タブは予約ID単位で表示する。同じ相手だからという理由で行を統合しない。各タブの未読を別々に持ち、現在の役割以外の本文・プレビュー・未読一覧は取得しない。

DM一覧は相手の役割別表示名・アイコン・最新文章・日時・未読・停止状態を表示。全件／未読／アーカイブを用意。DM一覧に予約内容・予約状態を自動表示しない。受信者本人には役割ごとの未読を本人用画面で確認できるが、相手や共通の公開プロフィールへ渡さない。

**DM-06：テキストと画像を送れる。** 既存予約メッセージに合わせ、テキストは最大1,000文字、画像は1送信1枚・10MiB以下・JPEG／PNG／WebPとする。文字だけ、または画像だけを送信でき、同一送信で本文と画像は混在させない。空送信は不可。改行・日本語・絵文字対応、日本語変換確定で誤送信しない。画像選択後はプレビューと送信ボタンで宛先・操作役割を確認できる。

画像の拡張子だけでなく内容・MIMEを検証する。EXIF等の位置情報・端末情報と元ファイル名を相手へ渡さず、向きを補正した配信用画像を作る。DMの非公開保存先を予約添付と分け、画像取得のたびに本人認証と固定された参加役割を確認する。リンクを知るだけでは他人・逆役割の参加者は取得不可。公開URLやアカウント共通IDを含むURLを返さない。外部通知に画像・サムネイルを添付しない。

送信者は自分の画像を削除でき、双方の会話で「画像は削除されました」と表示する。DM停止・ブロック後も自分の画像削除は許可し、接触操作と分ける。削除後は旧URL・サムネイルも取得不可。保存期間・通報保全はDM-18に従う。既存予約画像の操作は予約チャット内で継続し、DMへ移さない。

送信中／送信済み／失敗を区別し、失敗時は再送可能にする。テキスト・画像の両方に送信キーを持ち、同じキーの再送で本文・画像・通知を増やさない。異なる内容で同じキーを使えば409。画像は内容の同一性をサーバーで照合する。下書きと未送信画像はメモリ内で役割・DMごとに保持し、ログアウトで消す。画像保存後の送信拒否・失敗で残る一時ファイルも清掃する。

既読は会話が前面にあり500ms以上表示された受信メッセージだけをまとめて更新する。画像も受信メッセージとして扱い、予約チャットの既読を同時に変更しない。一覧は画像本文の代わりに「画像」と表示する。

一覧30件、本文50件を基本とし、過去を追加読込できる。表示中は原則5秒で差分更新し、背面や通信断では停止／間隔調整する。入力中表示は同じDM・役割内に限り8秒で失効する。他の役割でオンラインか、入力中かは知らせない。

**4. 予約チャットとの境界（DM-07〜08）**

**DM-07：予約チャットは予約IDのまま維持する。** DM本文・画像・既読・停止状態を予約チャットへ移行・複製・同期しない。予約メッセージもDMへ取り込まない。予約R1・R2はそれぞれ従来の予約別チャットを使い、初期表示に事前DMの本文を入れない。予約を直接作成してもDMを自動作成しない。

「予約チャットが始まる」は既存の予約生成・メッセージ閲覧条件に従うことであり、新たに決済完了をチャット解放条件にする意味ではない。DMと予約の機能は独立しているため、DMを停止・アーカイブしても既存予約は変更しない。予約の完了・失効・キャンセルでもDMを自動で閉じない。

**DM-08：予約導線は最小限にする。** DMには当該キャストの既存予約画面へ進む「予約する」を置く。初期版では専用の予約案内カード、予約状態の同期、DMと予約チャットの相互リンク、本文引用、DMからの特別価格提示を必須にしない。相談内容を予約条件として自動転記しない。

予約時は現在の利用者役割・対象キャスト、ブロック、本人確認・年齢確認、公開状態、空き枠、料金・割引、見積もり期限、決済等を既存フローで検証する。DMをしていない利用者も直接予約できる。DM受付OFFは予約受付停止を意味しない。

効果測定が必要なら、内部に起点DM IDを任意で記録できる。ただしサーバーで利用者とキャストの向きを照合し、相手向け予約APIへそのIDやDM本文を返さない。この計測用参照がない場合でも予約・チャットは成立する。

**5. 共通ブロック（DM-09〜11）**

**DM-09：キャストがブロックした対象から、DMと新規予約の両方を受け付けない。** DM用と予約用に独立したブロック設定を作らず、1つの共通判定を呼ぶ。受付OFF、DM停止、ミュートとは区別する。利用者側がキャストをブロックする場合にも同じ関係に対する接触を停止できる。

**ブロックは役割付きの組み合わせ単位で確定。** キャストBが利用者Aをブロックした場合、利用者A→キャストBのDM・予約を止める。利用者B→キャストAの逆役割には波及しない。どちら側が設定しても、同じ向きの関係で双方の送信を停止する。

ただし、既存のアカウント単位ブロックは、設定時の役割を推測して移行・縮小・解除しない。従来の範囲を持つ旧設定として保持し、新方式の役割別ブロックと合わせて判定する。旧設定の解除はその設定をした本人の明示操作で行い、新方式だけの解除で旧設定を消さない。旧設定を移行・読込しただけで過去予約を一括キャンセルしない。

ブロック画面にはその役割の相手だけを表示する。別役割の名前・画像や「この相手は別役割で活動しています」といった情報を出さない。拒否される側には「現在この相手への相談・予約はできません」等の共通文言を返し、設定元の役割や別プロフィールを知らせない。

**DM-10：判定箇所を統一する。** ボタン非表示だけで済ませず、次の経路で現在のブロックをサーバー確認する。

| 経路 | ブロック後の扱い |
|---|---|
| DM開始・既存DMの文章送信 | 拒否。キャスト側からも送信不可とし、解除後に再開 |
| DMの入力中・新たな既読通知・外部通知 | 相手へ配信しない。配信予定も実行前に再判定 |
| 検索・公開詳細から予約へ進む経路 | 既存の非表示条件を維持し、予約のサーバー認可でも拒否 |
| 見積もり作成 | 拒否。DM経由か直接かを問わない |
| 既存見積もりを使った予約作成 | ブロック前の有効見積もりでも拒否。今すぐ／日時指定、無料／有料すべて対象 |
| 未確定予約の新規決済認証開始・再開 | 外部決済呼出し前に拒否 |
| 申込済み予約の承諾・承諾につながる変更確定 | 再確認し、ブロック中の新たな受入れを拒否 |
| 該当する既存予約チャットへの新規投稿・画像・typing | 接触経路の迂回防止として双方を送信不可にする。既存のクローズ条件も引き続き適用 |
| 旧出張リクエスト経由の送信 | 同じ共通判定を適用し、DM以外への迂回を防ぐ |

ブロック保存が完了した後に認可される操作は拒否する。送信／予約作成とブロック更新が同時の場合は、サーバー内で順序を確定させる。決済サービスにすでに送った処理はDBだけで取り消せないため、戻り処理や決済イベント受信時に再確認し、自動承諾へ進めない。必要な決済認証解除・返金は既存の正式手順で扱う。

**DM-11：キャストのブロックに伴うキャンセル・精算。** 利用者からのご提案を踏まえ、施術開始前は「キャストがブロックすると、該当する予約をキャンセルし、利用者負担ゼロにする」を推奨仕様とする。自動処理の境界と開始後の例外は提案段階で、詳細は[追加決定・推奨仕様](追加決定・推奨仕様.md)に定める。

対象は同じ利用者→キャストの組み合わせの未開始予約すべて。承諾済み・移動中・到着済みはキャスト都合キャンセル、承諾前は見送り／決済中止の既存状態へ進める。DMと該当予約チャットの双方の送信を止める。開始前の確認画面に対象予約・件数・返金予定額を出し、「ブロックして予約をキャンセルする」で確定する。逆役割の予約や終了済み予約は対象にしない。

施術中、キャスト完了報告後、未着等の係争確認中は、ブロックと送信停止は即時に行い、自動返金は運営確認へ回す案とする。完了済み予約はブロックだけで取り消さない。利用者側からのブロックも接触は停止するが、自動キャンセル・無料返金の契機にはしない。利用者がキャンセルする場合は既存の利用者側条件で行う。

請求確定前はカード利用枠の解除、請求済みは支払済み額から既返金額を引いた残額を全額返金する。利用者へキャンセル料・手数料を差し引かない。無料予約に返金APIを呼ばない。ブロック・予約取消と外部返金の完了は別状態で管理し、返金失敗でも接触や予約を再開しない。二重処理を防いで再試行し、運営へ通知する。カードへの反映完了前に「返金完了」と断定しない。

予約確認・精算状況・運営問い合わせの閲覧は残す。ブロック解除で予約を復活させたり、抑止した文章・通知を後送したりしない。過去履歴は元の閲覧範囲とDM-18の期限で保持し、旧クローズ予約は再公開しない。予約キャンセル・返金などの業務通知は個人間の文章通知と分けて届ける。

**6. 受付設定・通知・運用（DM-12〜15）**

**DM-12：DM受付・停止。** キャストの事前DM受付は初期ONとし、本人が必要に応じてOFFにできる。OFFは新規DM開始だけを止め、すでに開始済みのDMへの返信は維持する。キャストが非公開になった場合は新規DM不可、既存の文章連絡は継続可。アカウント／キャスト活動停止・退会時は新規送信を止める。

双方が自分のアーカイブ・ミュート・DM停止を設定できる。アーカイブは自分の一覧だけ、ミュートは自分の外部通知だけに適用。DM停止中は双方のDM送信を止め、各自が自分の停止のみ解除できる。これらは予約受付や別役割DMへ波及しない。DM停止を予約チャットまで止めたい場合は、共通ブロックを使うことを説明する。

**DM-13：通知も役割・用途で分離する。** DM通知と予約メッセージ通知の種別・リンク・未読を区別する。DM通知リンクは受信者の正しい役割のDMへ、予約通知リンクは既存の予約チャットへ戻す。他役割で開いた場合は本人に切替を案内し、本文を先に出さない。

プッシュ・メール本文は「新しいメッセージがあります」等とし、相手の名前、文章、他役割の活動、画像や住所を外部通知へ含めない。アプリ内では、選択中の役割に該当する通知本文だけを表示する。本人専用の未読件数表示と、相手へ見せる情報を分ける。

本文保存後に通知を送信する。配送失敗でも保存済み文章を失敗扱いにしない。DMのプッシュは1分以内の連投をまとめ、メールは5分未読後・同じDMの受信者に30分以内の再送なしを初期値とする。既読、ブロック、停止、退会、通知OFF、ミュートは配送直前に再確認する。まとめ配信キーはDM ID×受信者側役割×チャネルで区別する。

DM通知設定は役割ごとに設定可能とし、メールは初期ONを案内してOFFにできる。端末のプッシュ許可は変更しない。既存予約の業務通知をDMのまとめ配信へ巻き込まない。

**DM-14：送信上限・返信支援。** 新規相談は利用者として直近24時間で別キャスト5人まで、相手の初回返信前は初回を含む3件まで、1アカウントのDM送信は1分20件までを初期値とする。文字と画像は各送信1件として同じ上限に数える。上限は設定で調整可能にする。予約ができてもDMの返信前上限を自動解除しない。予約連絡は別チャットを使う。

内部の不正防止でアカウント単位の制限を共有しても、どの別役割で上限に達したかを相手へ出さない。既存の外部連絡先検知を再利用し、検知だけで自動アカウント停止しない。キャスト一覧で未返信の初回相談を確認でき、24時間を超えたものを要確認として示す。人が送ったテキスト・画像のどちらも返信と数え、自動通知や既読は数えない。画像の連絡先を既存の文字列検知で検出できるとは扱わず、画像も原文通報の対象とする。

**DM-15：DMだけでも通報できる。** 予約なしで会話または特定文章を通報できる。原文の閲覧権限と役割をサーバー確認し、相手に別役割の身元を開示せずに管理者へ連携する。ブロックと通報は別操作として記録する。管理者は必要な範囲で内部アカウントを照合できるが、通常の参加者APIとは権限を分け、閲覧・対応・内部メモを監査する。

**7. 既存機能・導入範囲（DM-16〜19）**

**DM-16：予約メッセージを移行しない。** 既存booking_messages、予約ID別URL、画像、既読、クローズ、管理者メモ、通報をそのまま維持する。前回確認した144件（旧クローズ124件を含む）をDMへ参照付け・複製・再公開しない。DMがない状態から追加するだけなので、予約履歴を集約する移行処理は不要。

ただし、共通ブロックの適用と役割別の送信者表示・公開IDへの変更は既存予約チャット側でも必要。本文を移行しないことと、現在の表示・認可を無条件で安全とみなすことを混同しない。既存の名前・ID・画像レスポンスに関する変更は、対応する画面も同時に修正し、予約別URLと文章・画像の操作を維持する。

**DM-17：初期版を単純化する。** 必須は役割別DM、役割別の表示・通知、既読、受付設定、通報、共通ブロック、既存予約画面への入口。前案の予約案内専用データ、統合タイムライン、予約カード、旧履歴移行、旧予約送信APIの廃止を取り除く。

出張リクエストは初期版で既存機能のまま残し、DMへ自動変換しない。DMを送っただけで出張リクエストを同時作成しない。将来、出張相談ボタンをDMへ一本化するかは別途判断する。今回は連絡機能全体を一度に置き換えない。

**DM-18：データの境界。** DM本文は既存同様に保存暗号化し、第三者へ公開しない。予約前DMの参加者情報を、メール・電話・本人確認・健康情報まで含む自分用AccountResourceから作らない。APIの明示的な許可項目だけを返す。DM・予約間で共通のアカウントIDが相手側に露出しないようにする。

**保存期間は推奨案。** 新DMの本文・画像は各送信から1年で自動削除する。新着・既読・アーカイブで過去の保存期限を延長しない。画像の本人削除は即時に非表示・取得停止、通常保存先から24時間以内に除去する。通報対象は必要部分だけ運営専用に保全し、利用者画面で復活させない。

退会時は送信・未配信通知を止め、相手向けの名前・写真・プロフィールリンクを直ちに退会表示へ置換する。退会者が送ったDM本文・画像は、通常の1年期限と退会90日後の早い方までに削除する。画像は退会時に相手からの取得も停止する。相手自身が送った文章は通常期限のまま。未返信DMだけで退会を拒否しない。

通報・返金トラブル等の対象は対応中に限って保全し、90日ごとに必要性を見直す。解決後は原則1年で削除し、特別な継続保全には理由・責任者・次回見直し日を記録する。バックアップの残存は通常保存先からの削除後最大35日を目標とし、復元時に削除履歴を先に適用する。これらは法定期間ではなく運用提案で、採用前に既存規程・バックアップ構成との整合を確認する。[保存期間の詳細と根拠](追加決定・推奨仕様.md)

この期限を既存予約チャットへ一括適用しない。予約・決済・返金の記録は別の保存方針で保持する。アーカイブ・ブロックはそれ自体では本文削除操作としない。

**DM-19：導入と障害対応。** 追加テーブルと役割別APIを作り、共通ブロックと既存の対外表示を先に確認する。stagingで逆役割の2つのDMと複数の予約チャットを使って検証し、協力キャストのDM受付ONから公開する。

DM機能フラグOFFでも予約・予約チャット・共通ブロックは動作する。障害時はDM新規受付・送信・外部通知を止め、保存済みDMの閲覧と既存予約を維持する。追加データの削除や旧予約チャットへの書き戻しは行わない。

同時20利用者・1DM1万件の合成データで一覧／差分取得p95が1秒以内、文章保存p95が2秒以内を目標として測定する。外部メール・プッシュの応答を文章保存に待たせない。スマートフォン、日本語入力、画面復帰、複数タブ、役割切替、通知リンクを確認する。

**8. 成果指標・実装順（DM-20）**

**DM-20：役割の向きを守って効果を測る。** 初回相談数、24時間以内の初回返信率、同じ利用者→同じキャストへの7日以内の初回予約・30日以内の利用完了を内部集計する。逆の役割の予約をDMの成果に含めない。テスト・管理者関与・無料／有料を分け、7日／30日の観測期間を満たした対象で確定率を出す。相手向け画面に兼任の有無や別役割の利用実績を出さない。
