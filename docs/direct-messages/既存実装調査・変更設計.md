| direct_message_participant_settings | thread_id、participant_role（user/therapist）、mute/archive/pause。所有者から役割を検証し、他側を書き換え不可 |
| direct_messages | public_id、thread_id、sender_role、message_type、暗号化本文、添付の非公開保存参照・MIME・サイズ・削除時刻、client_message_id・内容照合値、sent_at、read_at、expires_at、moderation関連。予約IDは持たない |

| 役割別通知設定 | 所有アカウント＋操作役割＋DMチャネル。相手向けAPIには出さない |

| 保存・削除・保全 | 削除予定、本文を含まない削除履歴、運営専用の通報証拠・保全期限。予約データとは独立 |
| 共通ブロック | 下記の範囲方針に従い、単一サービスから新旧保存先を判定する |

所有アカウントの照合はサーバー内部だけで行う。プロフィールの所有者を移し替えない。プロフィールを作り直しても既存ブロックを回避できないよう、実効ブロックの判定には不変の内部アカウントを利用する。

利用者表示名の現行保存先Account.display_nameは「利用者側の表示名」としてのみ参照できる。キャスト公開名が空なら汎用表示とし、Account.display_nameへフォールバックしない。本文送信者はサーバーがthreadと操作役割から決定し、任意のsender_account_idや他人のprofile_idを受け入れない。

予約は従来のbookingsとbooking_messagesに保存し、DMとは独立する。conversation_entries、conversation_bookings、旧履歴索引、予約カード用イベントテーブルは作らない。DM起点の予約を計測する場合のみ、非公開の任意参照を別に持てる。これをメッセージ取得の結合条件や閲覧許可に使わない。

**3. 相手向けAPIの出力境界**

DMのParticipantResourceはrole、role_profile_public_id、display_name、許可したavatar_urlだけを基本とし、serializerの許可リストで返す。所有者Accountのpublic_id、roles、last_active_role、therapistProfileとuserProfileの同時展開、共通メール・電話は返さない。本人専用の/meが全保有ロールを返すことと、相手向けに返すことを区別する。

予約チャット・予約詳細・旧出張リクエスト・ブロック一覧・通報表示にも、共通IDや利用者名がキャストの人格と結び付く経路がないか確認する。本件で使う対外的な応答では、役割別プロフィール表現へ合わせる。特にBookingMessageResourceのsender、BookingMessageControllerのcounterparty、BookingResourceのcounterparty/canceledBy、AccountBlockResource、TherapistTravelRequestResource、ReportResourceを確認する。

旧レスポンスのsender_account_idに別種のプロフィールIDを入れて「互換」と称しない。sender_profile_id等へ明示的に変更し、フロントの型・表示・ブロック操作も更新する。一般クライアントで必要な所有者IDをサーバーが解決し、ブラウザへ渡してから再投稿させる設計をやめる。既存の予約ID・予約メッセージID・画面URL・本文保存先は維持する。

キャストの写真URLから所有Account.public_id等を読み取れないことも確認する。写真の利用者用／キャスト用の範囲を保ち、未設定時に他方を代用しない。共有キャッシュには操作者・操作役割・対象DMを含め、ロール切替前のAPI応答を後から新画面へ適用しない。

**5. 共通ブロックの設計**

**確定：新規ブロックは役割付き関係単位、旧AccountBlockは従来の範囲を保持する。** 新規保存先はrole_relationship_blocks等を追加し、user_account_id、therapist_account_id、blocker_roleを保持する。この2つの所有アカウントIDは役割順を固定し、大小順へ正規化しない。会話単位のブロックにせず、同じ向きの全DM・予約に適用する。各側は自分のblocker_roleの行だけ解除でき、相手側のブロックは残る。

共通判定は「既存account_blocksにどちらか向きの設定がある」または「該当する利用者→キャストの役割付き関係にどちらかのblocker_roleがある」で拒否する。逆役割の新規行は検索対象にしない。公開された役割別プロフィールから所有アカウントをサーバーで解決するため、プロフィール再作成でも回避できない。

既存行には設定時の役割がないため、自動的に役割別テーブルへ移さない。旧ブロックの一覧は新たな別役割の身元を補完せず、本人向けの不透明なblock IDから解除対象を特定する。新方式の解除が旧行や逆役割の行を削除してはならない。逆役割への適用は行わない。旧行の存在確認・データ追加だけでは過去予約の取消を発火させない。

共通サービスの入力は内部の利用者Account、対象TherapistProfile／その所有Account、操作種別（DM、新規見積、予約作成、新規決済、承諾、予約文章等）。最低限「停止か」「内部監査用の根拠」「UIへ出せる汎用理由」を返す。相手へブロック設定元の詳細を返さない。

DM受付OFF・DMのpause/mute/archiveは共通ブロックではなく、予約への影響を持たせない。旧予約クローズもその予約だけの閲覧・送信条件であり、新DMの受付判定にコピーしない。

| BookingStatusController / ScheduledBookingPolicy / BookingStatusTransitionService | acceptおよび承諾につながる調整確定でロック内に確認。ブロック後の新たな承諾を拒否 |

存在しないブロック行に対する単なるSELECTだけでは、並行insertとの順序を保証できない。安定した関係キーの行ロック等でブロック更新と新規送信・予約作成を同じ順序で制御する。競合試験を受け入れに含める。

外部決済の通信中にブロックされた場合、成功した外部処理をDBロールバックだけで消せるとは扱わない。新規受入れを止め、未確定予約の認証解除・必要な正規返金を重複なく処理する。キャストが今回新たにブロックした場合、開始前の該当予約すべてを取消・利用者負担ゼロとする案へ変更する。施術開始後・係争中は運営確認、完了済みは取消対象外とする。利用者側のブロックだけでは無料取消しない。[状態別の定義と追加実装](追加決定・推奨仕様.md)を参照。

**6補足. ブロックに伴う予約取消と画像対応**

既存BookingCancellationPolicyはキャスト都合をキャンセル料0円とするが、payment_actionをvoid_authorizationにする。BookingPaymentIntentCancellationServiceはsucceededをそのまま返すため、請求済み全額返金は現行処理の単純呼出しだけでは成立しない。決済状態で認証解除／残額全額返金を分岐し、複数の認証・請求・既返金も照合する必要がある。

新規キャストブロックの確認画面には同じ向きの全対象予約と影響額を返す。保存時に関係・予約をロックして状態を再確認し、ブロック・取消状態・決済対応ジョブを一体で保存する。複数予約の一部失敗でもブロックを巻き戻さず、予約ごとの対応状態を持って再試行する。StripeRefundGatewayの現行createには明示的な冪等キーがないため、再送・応答不明・Webhook重複でも二重返金を防ぐ設計を追加する。予約取消・売上台帳・キャンペーン復元・キャスト都合キャンセル件数・業務通知も一度だけ反映する。係争中・開始後の保留対象を正常完了と表示しない。

DM画像の利用仕様はBookingMessageController.storeに合わせる。最大10MiB、JPEG/PNG/WebP、文字と画像は別送信。旧画像配信は期限付き署名URLでviewer_roleを使うが、DMでは署名だけを閲覧権限にせず、取得のたびに認証と役割所属を検証する。元ファイル名・EXIF・共通IDを出さない。保存先は非公開とし、暗号化・アクセス権を設計する。画像削除はメタ情報の削除表示、通常保存先、派生画像、取得権限を一貫して更新し、通報証拠は別保全とする。期限処理・退会処理は原文や画像をバックアップ復元で再公開しない。[詳細](追加決定・推奨仕様.md)

**7. 通知・既存機能への影響範囲**

新しいnotification_typeをdirect_message_received等で区別し、AppNotificationObserverの従来同期配送からこの種別だけを除外する。本文・配信予定を同時保存し、確定後にDBの配信予定を毎分の定期実行等で回収する。DMのまとめ配信と予約チャット通知を同じキーにしない。既読・停止・ミュート・ブロック・退会を配送直前に再確認する。

再試行は初回に加え1分・5分・30分後の最大3回を初期案とする。外部送信の応答不明時に完全な一度だけの到達を保証するとは説明しない。保存と通知予定は一意制約で重複させず、本文や認証情報をエラーログへ出さない。

DMと予約チャットは同じ見た目の部品を共有しても、取得API・投稿先・下書き・既読・通知・cache keyを別にする。新DMへの旧予約メッセージの入力、既存画像の移し替え、旧URLのDMへのリダイレクトは行わない。出張リクエストの新規・過去記録も初期版では維持し、共通ブロックと役割別表示だけを揃える。

**9. 計測**

direct_message_started、first_human_reply、direct_message_sentを、役割付きDMのIDでサーバー記録する。booking_created／booking_completedとの照合は「利用者Account → キャストProfile」の同じ向きだけとする。内部で同一アカウントを集計する場合も、相手向けプロフィールや通知へ別役割の活動を返さない。

7日転換率は7日経過した相談を対象に、同じ向きの初回予約を数える。ペア単位の率と利用者人数を分ける。過去の予約チャット文数をDM開始・返信数に足さない。30日完了も観測期間を満たした対象だけで確定率を出す。本文・写真URL・共通アカウントIDを外部アクセス解析へ送らない。
